# アーキテクチャ

本リポジトリの層と依存の向きを定める。実装より先に決める文書であり、実装とずれたら実装に
合わせて本文書を直す。

参照: Issue #2「v1仕様: Git LFS custom transfer agentとrclone保管境界を定義する」

## 1. 目的

Git LFS（Git Large File Storage。大容量ファイルの実体の代わりに参照情報をGitへ記録する
仕組み）のstandalone custom transfer agentとして動作し、rclone経由の外部保管先へ
Git LFS objectを保存・取得するコマンドラインプログラムを提供する。

複数のPCと複数のGitリポジトリが同じ転送基盤を共用する。利用側のプロジェクトは
Google Drive、認証トークン、PC固有のパスを知らない。

## 2. 層の定義

層はクレートで表す。依存の向きはCargo.tomlが強制する。依存を書かなければその層のコードは
コンパイルできない。

| 層（クレート） | 何を持つか | 何を知ってよいか |
|---|---|---|
| `gitlfs-tools-domain` | オブジェクト識別子、期待バイト数、保管先オブジェクトパス、一時ファイルパス、プロファイル名、転送タイムアウト、検証済みローカルファイル、保管エラーの分類 | なし |
| `gitlfs-tools-storage-port` | `オブジェクト保管庫`トレイトとその戻り値型 | `domain` |
| `gitlfs-tools-config` | プロジェクト設定、PC設定、論理プロファイルの解決 | `domain` |
| `gitlfs-tools-transfer` | 資産転送サービス（アップロード・ダウンロードのユースケース） | `domain`, `storage-port` |
| `gitlfs-tools-rclone` | rcloneを子プロセスとして起動する`オブジェクト保管庫`の実装 | `domain`, `storage-port` |
| `gitlfs-tools-local` | ローカルディレクトリを保管先とする`オブジェクト保管庫`の実装 | `domain`, `storage-port` |
| `gitlfs-tools-protocol` | Git LFS custom transfer protocolのJSON入出力と日本語ドメインモデルへの変換 | `domain`, `transfer` |
| `gitlfs-tools-cli` | コンポジションルート、実行ファイルの入口、導入コマンド | 全層 |

依存の向きは表の上から下だけとする。逆向きの依存を書くとCargoが循環依存として拒否する。

### 層の外側にあるもの

`xtask`はリポジトリ内ツールであり、本体の層に属さない。本体クレートへ依存しない。

## 3. 主要な設計判断

### 判断1: rcloneアダプタは設定ファイルの形式を知らない

`gitlfs-tools-rclone`は`gitlfs-tools-config`へ依存しない。rcloneリモート名・保管先基底パス・
一時ディレクトリ・転送タイムアウトを`domain`の型として構築時に受け取る。TOMLのkey名や
設定ファイルの置き場所を知るのは`gitlfs-tools-config`だけである。

この向きにすると、設定ファイルの形式を変えてもアダプタが影響を受けず、アダプタの試験に
設定ファイルが要らない。

### 判断2: プロトコルアダプタは保管庫の実装を知らない

`gitlfs-tools-protocol`は`gitlfs-tools-rclone`へ依存しない。`init`イベントで必要になる
「設定を読み、プロファイルを解決し、rcloneの起動可否を確かめ、資産転送サービスを組み立てる」
一連の手続きは、`gitlfs-tools-protocol`が定義する`転送セッション開始境界`トレイトの背後に置く。
実装は`gitlfs-tools-cli`が持つ。

コールバックを渡す形にしない。開始する操作は名前を持つ型のメソッドとして表す
（グローバルCLAUDE.md「サービスの依存保持とコールバックの限定」）。

### 判断3: 外部仕様で固定される名前だけ英語を保つ

Rust内部で意味を表す識別子は日本語で命名する。Git LFS protocolのJSONフィールド名、
rcloneのCLI引数、TOMLのkey、Git設定のkey、Cargoのパッケージ名は外部仕様が決めるため
英語のまま保持する。外部プロトコルを独自に翻訳しない。

Cargoのパッケージ名がASCIIしか受け付けないため、クレート名は英語である。クレート内部の
モジュール名・型名・関数名は日本語で書く。

### 判断4: 検証済みであることを型で表す

アップロードできるのは、ローカルファイルのバイト数とSHA-256をオブジェクト識別子と
照合し終えた入力だけである。この「検証済み」という状態を`検証済みローカルファイル`という型で表し、
検証を通らない値が`オブジェクト保管庫::アップロードする`へ到達できないようにする。

### 判断5: 保管先のオブジェクトは変更不能として扱う

最終オブジェクトのパスは内容から決まる（`<基底パス>/lfs/objects/sha256/ab/cd/<64文字の識別子>`）。
同じ内容は必ず同じパスへ落ちるため、既に存在するオブジェクトへ再度アップロードしない。
内容の更新は新しい識別子のオブジェクトの追加で表す。

### 判断6: 標準出力はGit LFSとの通信専用にする

Git LFSはagentの標準出力を1行1JSONのプロトコルとして解釈する。診断情報は標準エラー出力へ
書く。rcloneの標準出力と標準エラー出力は`gitlfs-tools-rclone`が捕捉し、agentの標準出力へ
流さない。この規律を破ると、Git LFS側のJSON解析が壊れて転送全体が失敗する。

### 判断7: ダウンロードの一時ファイルはリポジトリの中に置く

`download`の`complete`で返した一時ファイルは、その時点でGit LFSの所有物になる。Git LFSは
それをリポジトリの`.git/lfs/objects/`へ`rename`で移す。`rename`はボリュームをまたげないため、
一時ファイルがリポジトリと別のドライブにあると転送が必ず失敗する。

そこで一時ファイルの置き場所を保管先の設定から切り離し、`git`へ問い合わせたGit LFSの保管
ディレクトリ（既定は`<Gitディレクトリ>/lfs`、Git設定`lfs.storage`があればそれ）の下の
`tmp/gitlfs-tools`へ固定する。この位置は`objects`と親を共有するため、同一ボリューム
であることが位置から決まる。問い合わせは`gitlfs-tools-cli`の`git_lfs_storage_directory.rs`が行い、
`init`の時点で1回だけ解決する。Gitリポジトリの外では解決できないため、`init`を失敗させる。

この決定により、PC設定の`temp_directory`は読まれなくなった。既存のPC設定ファイルを未知キーで
拒否しないため設定の受理は続けるが、値は使わず、`doctor`が「削除してよい」と報告する
（`gitlfs-tools-config`の`使われなくなった設定項目`）。

## 4. この段階でやらないこと

- **到達不能オブジェクトの自動削除**: Git履歴から参照されるオブジェクトを誤って消す危険が
  ある。削除の判定にはGit側の全参照走査が要り、v1の範囲を超える。
- **rclone以外の保存処理の直接実装**: Google Drive APIを直接叩く実装を持たない。保管先の
  差し替えはrcloneのリモート設定で行う。
- **保管先の自動移行**: 別のrclone対応先へ移すとき、既存のオブジェクト群の複製は利用者が
  rcloneで行う。照合コマンドは後続のIssueへ分ける。
- **プロジェクトごとの認証情報管理**: 認証はrclone自身のローカル設定だけが持つ。

## 5. 採用ライブラリ

本リポジトリは外部ライブラリを抑制的に採用する。採用したものと採用理由を次に記す。

| ライブラリ | 用途 | 採用理由 |
|---|---|---|
| serde / serde_json | Git LFS protocolのJSON入出力 | 公開仕様の実装であり、自作しても差別化にならない |
| toml | 設定ファイルの解析 | 同上 |
| sha2 | オブジェクト識別子の検証 | 暗号ハッシュの自作は健全性の検証コストが見合わない |
| uuid | 一時ファイル名の生成 | 衝突しない名前の生成規則は公開仕様である |
| thiserror | エラー型の定義 | 導出マクロのみ。実行時の振る舞いを持たない |
| directories | OSごとの設定ディレクトリの解決 | OSの慣習は第一原理から導出できない蓄積知識である |
| tempfile | テストの隔離ディレクトリ | テスト専用。本体の振る舞いに関わらない |
