## 実証の構成

`cargo xtask check-v1-acceptance`（`xtask/src/acceptance_check/`配下に実装、`cargo xtask verify`
の工程には含めない）が次を行う。

- `std::env::temp_dir()`直下に固有名の一時作業域を作り、終了時に必ず削除する。
- PC A・PC Bを、孤立させた`GIT_CONFIG_GLOBAL`（実ユーザーのglobal git設定を変更しない）と、
  本エージェントのPC設定ディレクトリ（`LFS_RCLONE_PC_CONFIG_DIR`環境変数で切り替え）を持つ別々の
  模擬環境として作る。両者は別々の`git clone`であり、作業treeもLFSキャッシュ（`.git/lfs`は
  クローンごとに独立）も共有しない。
- 保管先にはrcloneのlocal backend（一時ディレクトリをGoogle Driveの代役にする）を使う。
  資格情報は不要。
- originにはローカルの裸リポジトリ（`git init --bare`）を使う。standalone transfer agentが
  実バイト転送を保管先へ直接行うため、origin自体はGit LFSサーバーである必要がない。

`LFS_RCLONE_PC_CONFIG_DIR`環境変数により、PC設定の置き場所は問題なく切り替えられた。追加の
仕組みは不要だった。LFSキャッシュの隔離も、クローンごとに別々の`.git/lfs`ディレクトリを持つため
自動的に得られ、追加の作業は不要だった。

## 通常のgit cloneだけで取得できるかの答え

**通常の`git clone`だけではLFS対象ファイルを取得できない。** Issue #2 7.3節が想定する
4手順（自動downloadを抑止してclone→agentとprofileを設定→対象リポジトリで導入command
→`git lfs pull`）が必要になる構成である。

検証した経路は次のとおりである。PC B相当のmachineで`git lfs install --skip-repo`
（machine単位で一度だけ行う、git-lfsのglobal filter登録）は済んでいるが、本エージェントの
project単位の登録（`git-lfs-rclone-storage install`によるlocal git設定）はまだ行っていない
状態で、素の`git clone <origin>`を実行した。

結果は次のとおりである。

```text
Cloning into '<一時作業域>\plain_clone_check'...
done.
Downloading payload.bin (300 KB)
Error downloading object: payload.bin (dc6d3f0): Smudge error: Error downloading payload.bin
(dc6d3f01...): error transferring "dc6d3f01...": [0] remote missing object dc6d3f01...
error: external filter 'git-lfs filter-process' failed
fatal: payload.bin: smudge filter lfs failed
warning: Clone succeeded, but checkout failed.
```

`git clone`自体は成功したが、LFS対象ファイルのcheckout（smudge）が失敗し、working treeへは
実体が置かれなかった。原因は次の2つが重なることである。

1. originが素の裸リポジトリであり、Git LFSの通常のbatch API（`/info/lfs`）を持たない。
2. project単位のstandalone transfer agent設定（`lfs.standalonetransferagent`のlocal git設定）を
   まだ行っていないため、本エージェント経由の取得にも切り替わらない。

一方、Issue #2 7.3節の4手順（`GIT_LFS_SKIP_SMUDGE=1 git clone` → `git lfs install --local` →
`git-lfs-rclone-storage install` → `git lfs pull`）では、項目3の実証が示すとおり、PC Aと
同一のSHA-256・バイト数でファイルを取得できた。

## 使わなかった項目・気づいた点（実装の欠陥ではない運用上の注意）

- `git lfs install --skip-repo`（machine単位の初回導入）が登録するhookのglobal templateにより、
  以後の`git clone`がGitの「clone中に出所不明なhookが有効化された」保護（`post-checkout`hook）に
  引っかかる。これは正規のgit-lfs hookであり、Gitのエラーメッセージが案内する
  `GIT_CLONE_PROTECTION_ACTIVE=false`で回避できる。実運用のPCでも初回clone時に同じ警告が出うる
  ため、導入手順の文書（Issue #9）にこの注意を含めるとよい。
