# トラブルシューティング

この文書は、大容量資産の取得や保存が失敗したときに、どこを見て何をすればよいかを説明する。日常の操作そのものは [日常操作.md](日常操作.md) が扱う。

失敗したときに最初に行うことは1つだけである。

```powershell
# 実行場所: 対象のGitリポジトリのルート
gitlfs-tools doctor
```

## `doctor` の読み方

`doctor` は現在のリポジトリとPCの設定を12項目にわたって確かめ、各項目を `[OK]` または `[不足]` として表示する。不足が1つでもあれば終了コードは1になり、すべて揃えば0になる。12項目とは別に、`doctor` は判定しない `[情報]` の行を2つ表示する。先頭に出るのは実行中の `gitlfs-tools` の版であり、8番の次に出るのは保管先にあるオブジェクトの数である。この2行はどちらも合否を判定せず、終了コードにも影響しない（後述の「判定しない2行: 版とオブジェクトの数」）。

### 12項目の一覧

| # | 項目名 | 何を確かめるか |
|---|---|---|
| 1 | Git LFSの導入確認 | `git lfs` を起動できるか |
| 2 | プロジェクト設定(.large-assets.toml) | 見つかるか、スキーマ版が対応しているか |
| 3 | PC設定 | 見つかるか、スキーマ版が対応しているか |
| 4 | 論理プロファイルの解決 | プロジェクトが参照するプロファイルがPC設定に定義されているか |
| 5 | 保管先ルートディレクトリの存在確認 / rcloneの起動確認 | 保管先へ到達できるか |
| 6 | ダウンロード一時ディレクトリの作成確認 | リポジトリ内の一時ディレクトリを作れるか |
| 7 | PC設定に使われなくなった項目が残っていないか | 読まれない設定キーが残っていないか |
| 8 | 保管先への書き込み確認 | 一時領域へ書き、読み戻し、消せるか |
| 9 | Gitのcustom transfer設定 | 4つのキーが登録されているか |
| 10 | このリポジトリでのGit LFSフィルター登録確認 | `git lfs install --local` を実行済みか |
| 11 | このリポジトリのGit LFSフックが標準の内容かの確認 | Git LFSのフックにGit LFS以外の内容が混ざっていないか |
| 12 | .gitattributesのGit LFS追跡パターン確認 | `filter=lfs` の行が1つ以上あるか |

5番の項目名は保管方式によって変わる。ローカルディレクトリ方式では「保管先ルートディレクトリの存在確認」、rclone方式では「rcloneの起動確認」と表示される。保管方式がまだ決まっていない段階（4番が未解決の段階）では「保管先への到達確認」と表示される。

8番は読み取りだけでなく書き込みを確かめる。保管先の権限設定によっては「読めるが書けない」状態がありえ、その状態は `git push` まで分からないためである。確認は一時領域（`<base_path>/lfs/tmp/<UUID>`）へ小さなデータを書き、読み戻して比較し、必ず消す形で行う。最終オブジェクトの領域には一度も触れない。

11番は、既にGit LFSを別の方式で使っていたリポジトリのための項目である。利用者が `pre-push` フックへ独自の行（実体の送信を止める `GIT_LFS_SKIP_PUSH=1` など）を書き足していると、導入の1行目の `git lfs install --local` が `Hook already exists: pre-push` と表示して終了コード2で止まる。この項目は、その状態を導入の前に検出する。**フックが1つも無い状態は合格として扱う。** `git lfs install --local` をこれから実行する正常な状態であるためである。対処の全文は [プロジェクト導入.md](プロジェクト導入.md) の「既にGit LFSを別の方式で使っていたリポジトリへ導入する」が持つ。

12番は導入の設計上どうしても必要である。`.gitattributes` の編集だけを手作業として残したため、他の項目がすべて揃っていても、対象パターンが無ければ大容量ファイルは1つも追跡されない。この状態を機械で検出しないと、利用者は「設定は完了した」と誤認する。

### 判定しない2行: 版とオブジェクトの数

`doctor` は12項目の判定に加えて、`[情報]` の行を2つ表示する。

1行目は、実行した `gitlfs-tools` 自身の版である。この行は出力の先頭に出る。

```text
[情報] gitlfs-tools の版: 1.0.0
```

**この行は合否を判定しない。** 版が古いか新しいかを機械が決められないためである。この行の役割は、利用者が2台のPCの `doctor` の出力を並べたときに、最初の1行だけで版の一致を確かめられるようにすることである。版を揃える手順は [PC初期設定.md](PC初期設定.md) の「2台のPCでは同じ版を使う」にある。

もう1つは、保管先にあるオブジェクトの数である。この行は、8番（保管先への書き込み確認）の次に出る。

```text
[情報] 保管先にあるオブジェクトの数: 2件(共用の保管先全体。他のリポジトリが置いた分を含む)
```

**この行は合否を判定しない。** 数が0でも、利用者がまだ1件もpushしていないだけかもしれず、「まだ送っていない」と「送ったものが消えた」を件数だけでは区別できないためである。区別できないものを合否に使うと、導入した直後の正常な状態で必ず落ちる検査になる。

**数えるのは保管先全体である。** 保管先は複数のGitリポジトリで共用しており、この数には他のリポジトリが置いたオブジェクトも入る。したがって、利用者はこの数を自分のリポジトリのファイル数と突き合わせてはならない。

この行の役割は、保管先の実体が根ごと消えたことに人が気づく機会を増やすことである。以前は2桁だった数が0件になっていたら、利用者は次の節の `check-objects` で欠けたオブジェクトを特定する。

### 上から順に直せばよい

**項目には依存関係があり、その依存関係が出力に現れる。** 4番（論理プロファイルの解決）が決まらない間、5番・7番・8番は「プロファイルが解決できていません／先に設定の不足を解消してください」と表示される。したがって、**最初に出た `[不足]` から順に直せばよく、下の項目を先に調べる必要はない。**

なお、4番は2番と3番の両方が成功したときにだけ表示される。どちらかが失敗している間、4番の行は出力に現れない。

### 何も設定していない状態の出力

新しいGitリポジトリで `doctor` を実行すると、次のように表示される。この画面は故障ではなく、これから設定する状態を表している。

```text

       対処: init-projectで雛形を作成してください(探索の起点: <リポジトリのルート>)
```

## よくある失敗と実際の出力

### 保管先のドライブがマウントされていない

Google Drive for Desktop が起動していない、またはサインインしていない状態で `doctor` を実行すると、5番と8番が失敗する。

```text
[不足] 保管先ルートディレクトリの存在確認: 設定不備: 保管先のルートディレクトリが存在しません。PC設定のbase_pathと、ドライブがマウントされているかを確認してください
       対処: PC設定のbase_pathが指すディレクトリを作るか、保管先のドライブをマウントしてください
[不足] 保管先への書き込み確認: 設定不備: 保管先のルートディレクトリが存在しません。PC設定のbase_pathと、ドライブがマウントされているかを確認してください
       対処: 保管先の権限設定・接続を確認してください
```

対処は、Google Drive for Desktop を起動してドライブが割り当てられたことをエクスプローラーで確認し、PC設定の `base_path` がそのドライブ文字と一致していることを確かめることである。

同じ状態で `git push` を行うと、次のように失敗する。

```text
error initializing custom adapter "gitlfs-tools" worker 0: [9] 設定不備: 保管先のルートディレクトリが存在しません。PC設定のbase_pathと、ドライブがマウントされているかを確認してください
error: failed to push some refs to '<リモートのURL>'
```

**Gitのrefの更新も失敗するため、pushは丸ごとやり直しになる。** コミットは残っているので、原因を直して `git push` を再実行すればよい。

### 使われなくなった設定キーが残っている

PC設定に `temp_directory` が残っていると、7番が `[OK]` のまま注記を表示する。この注記は失敗ではないが、設定ファイルを整理する合図である。

```text
[OK] PC設定に使われなくなった項目が残っていないか
       注記: temp_directoryは読まれていません。削除してください(ダウンロードの一時ファイルはGit LFSがrenameで奪うため、リポジトリと同じボリュームに置く必要がある。置き場所をリポジトリ内(Gitディレクトリの下のlfs/tmp)へ固定したため、この項目は読まなくなった)
```

### 保管先のオブジェクトが無い

保管先からオブジェクトが消えている、または一度もpushされていない状態で `git lfs pull` を実行すると、コード11で失敗する。

```text
error transferring "bffc3894c5f7c9c172b0897879c14065221a92080c828d451543d85c200e250e": [11] オブジェクトが存在しません: bffc3894c5f7c9c172b0897879c14065221a92080c828d451543d85c200e250e
Failed to fetch some objects from '<リモートのURL>'
```

出力に現れるoidとは、Git LFS がファイルの内容から計算する64文字の識別子（SHA-256）のことである。

**ローカルディレクトリ方式では、この失敗には原因が2つあり、対処が違う。** 利用者は、そのoidの実体を持つPCで保管先の該当パスを見て、2つの原因を見分ける。次のコマンドの `G:\マイドライブ\git-lfs-rclone-storage` の部分を、利用者は自分のPC設定の `base_path` に読み替える。

```powershell
# 実行場所: どのフォルダでもよい（実体を持つPCで実行する）
Test-Path "G:\マイドライブ\git-lfs-rclone-storage\lfs\objects\sha256\bf\fc\bffc3894c5f7c9c172b0897879c14065221a92080c828d451543d85c200e250e"
```

- `False` が返った場合、保管先へオブジェクトを一度も送っていないか、保管先からオブジェクトが消えている。利用者は、実体を持つPCで `git lfs push --all origin` を実行して送り直す。
- `True` が返った場合、オブジェクトはマウント先に在り、クラウドへの同期だけが済んでいない。**この場合、`git lfs push --all origin` は効かない。** 対処は後述の「クラウドへの同期の遅れ」にある。

### 保管先のオブジェクトが壊れている

保管先のオブジェクトのバイト数がpointerの記録と食い違うと、コード13で失敗する。

```text
error transferring "8fbfc25d035668d80d94a2c213ed638aee5fa5cae6dc83589b3ddf5ed4cac8f4": [13] バイト数が一致しません(期待: 50000, 実際: 29)
Failed to fetch some objects from '<リモートのURL>'
```

バイト数は合うが内容が違う場合は、コード14（SHA-256の不一致）で失敗する。

どちらの場合も、保管先には壊れた内容のオブジェクトが既に存在する。**この状態も `git lfs push --all origin` では直らない。** agentは保管先に同じoidのオブジェクトが在ることだけを見て転送を省くため、内容が壊れていても送り直さないためである。保管先の該当ファイルを取り除いてから送り直す手順は実証していないため、この文書は手順として書かない。利用者は、この失敗が起きたら保管先の状態を調べる。

## 保管先の実体が失われたとき

保管先の実体は、`git lfs pull` が失敗するまで誰も欠落に気づかない。実際に、基盤の担当者が動作確認の後片づけで共用の保管先のディレクトリごと削除し、別のリポジトリが置いた12件のオブジェクトを巻き添えで消した事故が起きている。`check-objects` とは、この失敗を先に見つけるための道具のことである。

```powershell
# 実行場所: 対象のGitリポジトリのルート
gitlfs-tools check-objects
```

`check-objects` は、`git lfs ls-files` が挙げるオブジェクトが保管先に実在するかを1件ずつ確かめ、欠けているものを一覧で示す。すべて在れば終了コードは0、1件でも欠けていれば1になる。

### `doctor` との違い

**`doctor` の失敗は「設定を直せ」を意味し、`check-objects` の失敗は「実体を送り直せ」を意味する。** 利用者が取る行動が違うため、基盤はコマンドを2つに分けている。`doctor` は設定が揃っているかだけを見るため、実体が消えていても全項目が `[OK]` になる。

### 突き合わせは片方向である

`check-objects` は「`git lfs ls-files` に在るものが保管先に在るか」だけを見る。**`check-objects` は逆を見ない。** 保管先に在って `git lfs ls-files` に無いオブジェクトは、他のリポジトリが置いたものであり、共用の保管先では正常な状態であるためである。したがって `check-objects` は、他のリポジトリのオブジェクトを違反として報告しない。

### 点検の範囲

引数なしの `check-objects` は、現在のチェックアウトが参照するオブジェクトを点検する。過去の版のオブジェクトまで含めるには、利用者は `--all` を付ける。

```powershell
# 実行場所: 対象のGitリポジトリのルート
gitlfs-tools check-objects --all
```

`--all` は全履歴を対象にするため、過去の版の実体まで保管先に揃っているかを確かめられる。古いリポジトリでは点検の件数が増え、そのぶん時間がかかる。

### すべて在るときの出力

```text
点検の範囲: 現在のチェックアウト
点検したオブジェクト: 2件
保管先に見つからないオブジェクト: 0件
点検したオブジェクトはすべて保管先にある。
注記: この点検はGit LFSが参照するオブジェクトだけを見る。保管先には他のリポジトリが置いたオブジェクトも在るが、それは正常であり点検の対象ではない。
```

### 実体が失われているときの出力

```text
点検の範囲: 現在のチェックアウト
点検したオブジェクト: 2件
保管先に見つからないオブジェクト: 1件
[欠落] alpha.bin (oid: 583ed974f2ae7494044730e62cd834c90619e36d303f211075e4c9de68bed3b8): 保管先に実体がありません
対処: git lfs push --all origin <ブランチ名> を実行して実体を送り直す。再送は冪等であり、既に保管先に在るオブジェクトは転送されない。
注記: この点検はGit LFSが参照するオブジェクトだけを見る。保管先には他のリポジトリが置いたオブジェクトも在るが、それは正常であり点検の対象ではない。
```

`[欠落]` の行は、どのファイルの実体が失われたかと、そのoidを示す。事由は2つある。「保管先に実体がありません」は実体そのものが無いことを、「保管先の実体のバイト数が食い違います」は実体は在るが内容が壊れていることを表す。

### 欠落したときの復旧

利用者は、そのオブジェクトの実体を持つPCで次を実行する。ブランチ名の部分は、そのPCでチェックアウトしているブランチの名前に読み替える。

```powershell
# 実行場所: 対象のGitリポジトリのルート（実体を持つPCで実行する）
git lfs push --all origin <ブランチ名>
gitlfs-tools check-objects
```

再送は冪等であり、既に保管先に在るオブジェクトは転送されない。したがって、どれが欠けたかを利用者が数えて選ぶ必要はなく、全部を送り直してよい。送り直した後に `check-objects` をもう一度実行し、欠落が0件になったことを確かめる。

**バイト数が食い違う場合、この手順では直らない。** agentは保管先に同じoidのオブジェクトが在ることだけを見て転送を省くため、内容が壊れていても送り直さない（前節「保管先のオブジェクトが壊れている」と同じ理由である）。

### 実体を持つPCが1台も無いとき

どのPCにも実体が無い場合、`git lfs push` で送り直すものが無い。この状態からGitだけで実体を復元する方法は無い。利用者は、保管先のバックアップ、または元の素材から作り直す。

## エラー出力から対処へ到達する動線

agentが返すエラーは、角括弧の中に数字を含む。

```text
error transferring "<oid>": [13] バイト数が一致しません(...)
                             ^^
```

この数字が、次の表のコードである。**エラー出力の角括弧内の数字を読み、下の表を引き、対処の列に従う。** この動線は受入条件の実証で確認済みである。

## エラーコード対応表

Git LFS custom transfer protocol は `error.code` の値域を定めていない。本リポジトリでの割り当てをここへ固定する（Issue #2 10節、`gitlfs-tools-protocol` の `error_code.rs` が実装の正本）。`init` の `error` 応答、および `upload`・`download` の `complete` 応答に含まれる `error` のどちらでも、`code` はこの表のいずれかの値になる。

| コード | 意味 | 利用者が取るべき対処 |
|---|---|---|
| 1 | プロジェクト設定（`.large-assets.toml`）が見つからない | Git作業ツリーのルートに`.large-assets.toml`があるか確認する |
| 2 | PC設定が見つからない | 導入手順に従ってPC設定（`config.toml`）を作成する |
| 3 | PC設定を置くべき標準ディレクトリを特定できない | OS環境を確認する。通常は起きない |
| 4 | 設定ファイル（プロジェクト設定またはPC設定）の解析に失敗した | TOMLの構文とキー名を確認する |
| 5 | 設定のスキーマ版が対応していない | agentの版と設定ファイルの`schema_version`を合わせる |
| 6 | プロジェクトが参照する論理プロファイルがPC設定に未定義 | PC設定へ該当プロファイルを追加する |
| 7 | 設定ファイルの読み込み（ファイルI/O）に失敗した | ファイルの権限・破損を確認する |
| 8 | `init`時、rclone実行ファイルを起動できない。PC設定`rclone_executable`が指すパスが明示されている場合、またはPATH解決に委ねている場合のどちらでも起こる | 明示していた場合はそのパスを確認する。PATH解決に委ねていた場合はrcloneを導入するか、PC設定`rclone_executable`でパスを明示する |
| 9 | 保管操作の設定不備（rcloneリモート名・保管先基底パスが不正等） | PC設定の該当プロファイルを確認する |
| 10 | `init`時、rclone実行ファイルの起動確認（コード8の確認）を通過した後、リモートへの問い合わせ（存在確認）に失敗した | rclone自身の設定・認証情報を確認する |
| 11 | オブジェクトが保管先に存在しない | 保管先へ実体がアップロード済みか確認する |
| 12 | oidが64文字の小文字16進文字列として不正 | Git LFS側の破損を疑い、再取得する |
| 13 | 保存済みまたはダウンロード後のバイト数が要求と食い違う | 保管先の内容が破損していないか確認する |
| 14 | ダウンロード後のSHA-256がoidと食い違う | 保管先の内容が破損していないか確認する。再ダウンロードしても直らなければ保管先を調査する |
| 15 | ローカル一時ディレクトリの作成・読み書きに失敗した | リポジトリのGitディレクトリへの書き込み権限と空き容量を確認する |
| 16 | rcloneの子プロセス実行に失敗した（起動不能・非0終了・タイムアウトのいずれか） | rclone実行ファイルの状態、`transfer_timeout_seconds`、rclone側のログを確認する |
| 17 | stdinの1行がJSONとして解析できない | agentを起動しているGit LFSの版を確認する。通常は起きない |
| 18 | 未知の`event`を受け取った | agentを起動しているGit LFSの版を確認する。通常は起きない |
| 19 | 必須フィールドの欠落または不正（`init`の`operation`、`upload`/`download`の`oid`欠落等） | agentを起動しているGit LFSの版を確認する。通常は起きない |

Git LFS 自身が出すメッセージにも角括弧の数字が現れる。初回cloneで見る `[0] remote missing object` は Git LFS のメッセージであり、上の表とは無関係である。表を引くのは、メッセージの本文が日本語で書かれている場合に限る。

## `doctor` では検出できない失敗

`doctor` は設定の現在の状態を確かめる道具であり、時間が経ってから起きる失敗や、外部のサービス側の事情は検出できない。認証の失効・クラウドへの同期の遅れ・対象パターンの書き漏らしの3つがこれに当たる。利用者は、この3つを機械では確かめられないため、失敗したときに自分で思い出す必要がある。

### rclone方式でのGoogleの認証の失効

rclone方式で、自分で作ったOAuthクライアントの公開ステータスを「テスト中」のままにすると、**認証トークンが7日で失効する。** 失効するまでは `doctor` の全項目が合格するため、機械では検出できない。導入から1週間ほど経って `git push` や `git lfs pull` が突然失敗した場合、この失効を疑う。

対処と背景は [PC初期設定.md](PC初期設定.md) の「rclone を使う場合」にある。既定のローカルディレクトリ方式では、この失敗は起きない。

### クラウドへの同期の遅れ

ローカルディレクトリ方式では、`git push` の成功はマウント先への書き込みが完了したことを意味し、クラウドへの実際の送信は Google Drive for Desktop が後で行う。書き込みの直後に、送信した側のPCで電源が落ちたり回線が切れたりすると、pointer（実体の代わりにGitへ記録される参照情報）だけが先に共有される。`doctor` は自分のPCから見える状態しか確かめられないため、`doctor` は他のPCから見えるかどうかを検出できない。この状態は、取得する側でコード11として現れる。

**この状態を `git lfs push --all origin` で復旧することはできない。** 送信した側のマウント先には、オブジェクトのファイルが既に存在する。存在しないのはクラウド側だけであり、agentはローカルのファイルシステムしか見ないため、agentはこの2つの状態を区別できない。したがってagentは「保管先に既にある」と判断し、転送を行わない。この動作は、同じoidを再びpushしても保管先のオブジェクトが増えないという設計（[日常操作.md](日常操作.md) の「`git push`」）のとおりであり、agentの欠陥ではない。

**実行すると成功したと表示されるため、利用者は復旧できたと誤解する。** 次は、マウント先に同じオブジェクトが既に在る状態で実行した実測の記録である。

```text
=== git lfs push --all origin を実行 ===
Uploading LFS objects: 100% (1/1), 200 KB | 0 B/s, done.
=== 保管先のファイルの更新時刻(再送後) ===
2026-08-09 22:29:54.000000000 +0900   ← 1回目のpushのときと同じ。変わっていない
```

正しい復旧手順は次の3つである。

1. 送信した側のPCで、利用者は Google Drive for Desktop を起動し、サインインした状態と回線を回復させる。
2. 送信した側のPCで、利用者は Google Drive for Desktop のメニューを開き、アップロードの残り件数が0になったことを確かめる。
3. 取得する側のPCで、利用者は次を実行する。

```powershell
# 実行場所: 対象のGitリポジトリのルート
git lfs pull
```

rclone方式では、agentが保管先へ転送することそのものがクラウドへの送信であるため、この状態は起きない。

### 対象パターンの書き漏らし

`doctor` の12番は「`filter=lfs` の行が1つ以上あるか」だけを確かめる。**どの拡張子を追跡すべきかは `doctor` には分からない。** `*.psd` を追跡していて `*.fbx` を追跡していない状態は、12番を通過する。

大容量ファイルをコミットした後にリポジトリが重くなった場合、利用者は `.gitattributes` にその拡張子の行があるかを確かめる。いま追跡されているファイルの一覧は、次のコマンドで確認できる。

```powershell
# 実行場所: 対象のGitリポジトリのルート
git lfs ls-files
```

## それでも直らないとき

転送が失敗したとき、Git LFS は詳細をログファイルへ残す。直近のログは次のコマンドで読める。

```powershell
# 実行場所: 対象のGitリポジトリのルート
git lfs logs last
```

失敗が一度も起きていないリポジトリでは `No logs to show` と表示される。この表示は正常であり、故障ではない。

agentは診断情報をすべて標準エラー出力へ書く。標準出力は Git LFS との通信専用であるため、agentの出したメッセージはこのログの中に現れる。
