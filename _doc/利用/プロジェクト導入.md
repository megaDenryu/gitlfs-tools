# プロジェクト導入

この文書は、1つのGitリポジトリでこの基盤を使えるようにするまでの手順を説明する。ここに書く作業は**Gitリポジトリごとに1回**行う。同じPCで別のリポジトリを追加するときは、この文書だけを繰り返せばよく、[PC初期設定.md](PC初期設定.md) をやり直す必要はない。

**前提**: [PC初期設定.md](PC初期設定.md) が終わっていること。終わっていない場合、この文書の手順は途中で失敗する。

## いつ導入するか

判断の問いは「いまこのリポジトリの資産が大きいか」ではない。**利用者が問うべきなのは「これから大容量の資産が増える見込みがあるか」である。** 見込みがあるなら、増える前が最も安い。

この問いをこう立てる理由は、移行の費用が時間とともに一方向にしか増えないことである。

- 利用者がいま導入すれば、これから増える資産は最初からpointer（実体の代わりにGitへ記録される参照情報）だけがコミットに入る。追加の工事は要らない。
- 利用者が後で導入すると、その時点までに積んだ実体を履歴から抜く工事が要る。この工事は `git lfs migrate import` による履歴の書き換えを伴い、そのリポジトリを clone している全員がやり直すことになる。

したがって、**「まだ資産が大きくないから後で入れる」という判断は、費用を先送りにするだけである。** 実例を挙げる。あるリポジトリでは、追跡対象にした6282件の合計が29.4メガバイトしか無く、1メガバイト以上のファイルは1件だけであった。それでも導入したのが正しい判断である。そのリポジトリはこれから地形データを増やす予定を持っており、増えた後で入れると履歴の書き換えが要るためである。

## 全体の順序

```powershell
# 実行場所: 対象のGitリポジトリのルート
git lfs install --local
git-lfs-rclone-storage install
git-lfs-rclone-storage init-project --profile personal-large-assets
git lfs track "*.拡張子"
git-lfs-rclone-storage doctor
```

この5行が導入の全量である。以下、本文書が各行の動作を説明する。`personal-large-assets` の位置には、利用者はPC設定に書いた論理プロファイル名を入れる。

## 既にGit LFSを別の方式で使っていたリポジトリへ導入する

**対象のリポジトリが、この基盤より前からGit LFSを別の方式で使っていた場合、上の5行はそのままでは通らない。** 利用者は導入の前にこの節を読む。旧方式の痕跡は3箇所に残る。フック、`lfs.storage`、そして実体の送信を止める設定である。

利用者は、導入の前に次のコマンドで痕跡の有無を確かめられる。

```powershell
# 実行場所: 対象のGitリポジトリのルート
git-lfs-rclone-storage doctor
```

`doctor` の11番目の項目「このリポジトリのGit LFSフックが標準の内容かの確認」が、フックの痕跡を検出する。

### 手順1が `Hook already exists: pre-push` で止まる場合

旧方式がGit LFSのフックへ独自の行を書き足していると、`git lfs install --local` は次のように表示して終了コード2で止まる。

```text
Hook already exists: pre-push

	#!/bin/sh
	export GIT_LFS_SKIP_PUSH=1
	git lfs pre-push "$@"

To resolve this, either:
  1: run `git lfs update --manual` for instructions on how to merge hooks.
  2: run `git lfs update --force` to overwrite your hook.
```

**利用者は、旧フックの内容を控えたうえで `git lfs update --force` で上書きする。**

```powershell
# 実行場所: 対象のGitリポジトリのルート
Get-Content .git\hooks\pre-push
git lfs update --force
git-lfs-rclone-storage doctor
```

**控えを取る理由は、後で元の方式へ戻せるようにするためである。** 旧フックはGitの管理対象ではないため、上書きすると内容は復元できない。何が書いてあったかが分からなくなると、利用者は旧方式へ戻す判断そのものができなくなる。上の1行目の出力を、利用者は作業の記録として手元に残す。

`git lfs update --force` はGit LFSが登録する4つのフック（`pre-push`・`post-checkout`・`post-commit`・`post-merge`）を標準の内容へ書き換える。上書きが終わったら、利用者は手順1から順にやり直す。

### `lfs.storage` が設定されている場合

`lfs.storage` は、Git LFS がローカルの控えを置く場所を既定の `.git/lfs` から別の場所へ移す設定である。旧方式では、この設定で控えを別のドライブへ逃がしていることがある。

```powershell
# 実行場所: 対象のGitリポジトリのルート
git config --get lfs.storage
```

**この設定の解除は必須ではない。** この基盤は `lfs.storage` を読んで一時ファイルの置き場所を決めるため、設定が残っていても送信と取得は成立する。実運用で成立を確認している。

**それでも解除を勧める。理由は2つある。**

1. 旧方式の設定が作業コピーにだけ残ると、後でこのリポジトリを見た人が、どちらの方式で動いているのかを判断できなくなる。`lfs.storage` はGitの管理対象ではないため、他のPCからは見えない
2. 取得の経路を確かめたい場合は、解除して控えを空にする必要がある

**2番目は、導入直後の動作確認が何を確かめているかに関わる。** 控えの置き場に既に実体があると、`git lfs fetch` はそこから読んで成功する。利用者は「取得できた」と判断するが、保管先を一度も使っていない。この状態を避けるため、取得を確かめる前に利用者は控えを空にする。

```powershell
# 実行場所: 対象のGitリポジトリのルート
git config --unset lfs.storage
Remove-Item -Recurse -Force .git\lfs\objects
git lfs fetch --all
```

`Remove-Item` が消すのはローカルの控えだけである。保管先のオブジェクトと作業ツリーのファイルは消えない。

### 実体の送信を止める設定が残っていないか

`GIT_LFS_SKIP_PUSH=1` は、Git LFS が実体を送らないようにする設定である。この設定が効いたままだと、利用者がこの基盤を導入しても実体は保管先へ送られず、コミットにはpointerだけが積み上がる。

上の `git lfs update --force` はフックの中に書かれたこの設定を消すが、**利用者は他の場所にも書かれていないかを確かめる。**

```powershell
# 実行場所: 対象のGitリポジトリのルート
$env:GIT_LFS_SKIP_PUSH
git config --get-regexp "^lfs\."
```

1行目が空を返し、2行目の一覧にこの基盤が登録するキー以外が並ばなければ、送信を止める設定は残っていない。環境変数がPCの設定として登録されている場合は、利用者がシステムの環境変数の一覧からも消す。

## 手順1: このリポジトリでGit LFSのフィルターを有効にする

```powershell
# 実行場所: 対象のGitリポジトリのルート
git lfs install --local
```

Git LFS がファイルの実体とpointer（実体の代わりにGitへ記録される参照情報）を入れ替えるための設定を、このリポジトリだけに登録する。`--local` を付けるため、他のGitリポジトリには影響しない。

`Updated Git hooks.` と `Git LFS initialized.` が表示されれば成功である。`Hook already exists: pre-push` で止まった場合、利用者は「既にGit LFSを別の方式で使っていたリポジトリへ導入する」へ戻る。

## 手順2: agentをcustom transfer agentとして登録する

```powershell
# 実行場所: 対象のGitリポジトリのルート
git-lfs-rclone-storage install
```

このリポジトリのGit設定へ、実体の転送をこのプログラムに任せるための4つのキーを登録する。登録される内容は次のとおりである。

| キー | 値 |
|---|---|
| `lfs.customtransfer.rclone-storage.path` | agentの実行ファイルの絶対パス |
| `lfs.customtransfer.rclone-storage.concurrent` | `true` |
| `lfs.customtransfer.rclone-storage.direction` | `both` |
| `lfs.standalonetransferagent` | `rclone-storage` |

**すべて `git config --local` であり、そのリポジトリだけに効く。** `--global` は使わないため、他のGitリポジトリのGit LFSの動作は変わらない。

`--path` を省略すると、実行中の実行ファイル自身の絶対パスを登録する。そのため、`cargo xtask install-binary` が配置した実行ファイルからこのコマンドを実行すれば、`cargo clean` で消えない安定したパスが登録される。PATHが通っていない場合は `git-lfs-rclone-storage install --path <配置先の絶対パス>` の形で明示する。

## 手順3: プロジェクト設定を作る

```powershell
# 実行場所: 対象のGitリポジトリのルート
git-lfs-rclone-storage init-project --profile personal-large-assets
```

このコマンドは、リポジトリのルートへ `.large-assets.toml` を作る。既存のファイルがあれば、このコマンドは上書きせず失敗する。生成される内容は次の2行だけである。

```toml
schema_version = 1
profile = "personal-large-assets"
```

**このファイルは保管先を知らない。** 保管先の実体（ドライブ文字、rcloneのリモート名、絶対パス）はPC設定だけが持ち、プロジェクトは論理プロファイル名でPC設定を参照する。この分離により、2台のPCは保管先の指定を違えたまま、同じリポジトリを共有できる。

### `--profile` に渡す名前は新しく作らない

**利用者が `--profile` に渡すのは、PC設定に既に定義してある論理プロファイル名である。** 利用者はここでリポジトリのための名前を新しく考えない。論理プロファイル名が指すのは保管先であってプロジェクトではないため、**プロジェクト名を渡してはならない。** 1つのプロファイルを複数のリポジトリが共用することが、この基盤の設計上の意図である。

名前の意味と、プロファイルを分けてよい場合は [PC初期設定.md](PC初期設定.md) の「論理プロファイル名の決め方」が定める。利用者が使える名前が分からない場合は、PC設定ファイル（`C:\Users\<ユーザー名>\AppData\Roaming\git-lfs-rclone-storage\config\config.toml`）の `[profiles.<名前>]` の行を見る。

## 手順4: 対象パターンを `.gitattributes` へ書く

### 何を追跡対象にするか

**どの拡張子を追跡対象にするかが、導入で最も重要な判断である。** 一度追跡対象にしたファイルを戻す作業は履歴の書き換えを伴うため、高くつく。

追跡対象にしてよいものは、次の3つの性質を持つ。

- ファイルが大きい（目安として1ファイル1メガバイト以上）
- 内容が二進形式であり、Gitの行単位の差分が意味を持たない
- 版が増えるたびに中身の全体が置き換わる

追跡対象にしてはならないものを次に挙げる。

- テキスト形式の設定ファイルとソースコード。小さくてもGitの差分が意味を持つ
- ビルドの成果物。そもそもGitへ入れず `.gitignore` の対象にする
- 生成できるもの。生成の手順をコミットするほうが安い

判断の材料として、利用者はリポジトリ内の大きなファイルを調べる。

```powershell
# 実行場所: 対象のGitリポジトリのルート
git ls-files | ForEach-Object { Get-Item $_ -ErrorAction SilentlyContinue } | Sort-Object Length -Descending | Select-Object -First 20 Name, Length
```

### 画像を追跡対象にすると GitHub 上で差分が見られなくなる

保管先はGitHubではないため、GitHubから見ると追跡対象の画像はpointerのテキストにしか見えない。**利用者はPull Requestの画面で、画像そのものの表示も、変更前後の見比べもできなくなる。** この制約は保管先を何にしても変わらない。

利用者は用途で決める。

- テクスチャや素材として使う画像であり、GitHub上で見比べる習慣が無いなら、追跡対象にしてよい
- 画面のアイコンや説明用の図であり、Pull Requestで見た目を確かめているなら、追跡対象から外したほうがよい

### 汎用的な拡張子は、何が作っているかを調べてから決める

`.bin` のように用途を限定しない拡張子は、そのファイルを何が作っているかで判断が変わる。**利用者は、拡張子だけを見て追跡対象に加えてはならない。**

- そのファイルがプログラムの生成物なら、そもそもGitへ入れるべきでない。生成の手順をコミットするほうが安いため、利用者は `.gitignore` の対象にすることを先に検討する
- そのファイルを人が手で作った、あるいは外部から取り込んだのなら、追跡対象にしてよい

### 対象パターンを書く

```powershell
# 実行場所: 対象のGitリポジトリのルート
git lfs track "*.psd"
git lfs track "*.fbx"
```

`git lfs track` は `.gitattributes` へ1行を追記するコマンドである。追記される行は次の形をしている。

```text
*.psd filter=lfs diff=lfs merge=lfs -text
```

利用者は `.gitattributes` を直接編集してもよい。追記でも直接編集でも結果は同じである。

### この手順をコマンド化していない理由

導入コマンドは `.gitattributes` を生成しない。**Git LFS の対象パターンの正本は `.gitattributes` だけであり、他の設定ファイルへ重複させないためである。** もし `.large-assets.toml` にも対象パターンを書ける設計にすると、2つのファイルが食い違ったときにどちらが正しいかを決める規則が要る。規則を増やすより、正本を1つに保つほうが安全である。

手作業として残す代わりに、対象パターンが1つも無い状態は `doctor` の12番目の項目が検出する。

**既にコミット済みのファイルは、対象パターンを追加しても自動ではLFSへ移らない。** 追加後に新しくコミットするファイルからLFSの対象になる。過去のコミットも移したい場合は `git lfs migrate` を使うが、コミットのハッシュが全部変わるため、共有済みのリポジトリでは影響を確認してから行う。


12項目すべてが `[OK]` になり、終了コードが0になれば導入は完了である。

```text
[OK] Git LFSの導入確認
[OK] プロジェクト設定(.large-assets.toml)
[OK] PC設定
[OK] 論理プロファイルの解決
[OK] 保管先ルートディレクトリの存在確認
[OK] ダウンロード一時ディレクトリの作成確認
[OK] PC設定に使われなくなった項目が残っていないか
[OK] 保管先への書き込み確認
[OK] Gitのcustom transfer設定
[OK] このリポジトリでのGit LFSフィルター登録確認
[OK] このリポジトリのGit LFSフックが標準の内容かの確認

```

`[不足]` が出た場合の読み方は [トラブルシューティング.md](トラブルシューティング.md) が扱う。

## 手順6: 設定をコミットする

```powershell
# 実行場所: 対象のGitリポジトリのルート
git add .gitattributes .large-assets.toml
git commit -m "大容量資産の保管基盤を導入する"
```

この2ファイルをコミットすることで、同じリポジトリを使う他のPCが同じ論理プロファイル名と同じ対象パターンを受け取る。

## このファイルはコミットする / しない

| ファイル | コミットするか | 理由 |
|---|---|---|
| `.gitattributes` | **する** | Git LFS の対象パターンの正本である。他のPCと共有する必要がある |
| `.large-assets.toml` | **する** | スキーマ版と論理プロファイル名だけを持ち、PC固有の情報を含まない |
| Git設定（`.git/config`） | しない | Gitが管理対象にしない。`install` を各PCで実行して作る |
| PC設定 `config.toml` | しない | リポジトリの外にある。[PC初期設定.md](PC初期設定.md) の表を見る |
| 大容量資産の実体 | Gitには入らない | コミットに入るのはpointerだけである |

コミットに入る量は実測で確かめられる。300000バイトのファイルを対象パターンに合わせてコミットすると、コミットに入るのは131バイトのpointer本文であり、作業ツリーには300000バイトの実ファイルが置かれる。pointer本文は次の形をしている。

```text
version https://git-lfs.github.com/spec/v1
oid sha256:3cdc92c3d725c404c8cfaa26d17a7ff0420dac1c5fc5a837c8d819f07a9ee698
size 300000
```

`oid` の行に並ぶ64文字が、Git LFS がファイルの内容から計算した識別子（SHA-256）である。保管先でのオブジェクトの置き場所は、この識別子だけから決まる。

**認証情報をコミットしない。** rclone設定、OAuthトークン、client secret、PC設定、試験用の資格情報は、いずれもGit管理対象にしない。コミット前に `git diff --cached` を目視し、絶対パスと資格情報が入っていないことを確かめる。

## 初回clone

**通常の `git clone` だけでは大容量資産を取得できない。** これは不具合ではなく、Git LFS の仕組みから来る制約である。clone した時点ではまだagentが登録されていないため、Git LFS は実体の取得先を知らない。agentの登録はclone後にしか行えない。

**利用者はこの一連の手順を `clone` サブコマンドに任せられる。** 次の節がその使い方を説明し、その後の節が従来の4手順を残す。

### `clone` サブコマンドを使う

```powershell
# 実行場所: cloneしたい親ディレクトリ
git-lfs-rclone-storage clone <リポジトリのURL> [<ディレクトリ名>]
```

このコマンドは、次の5つを順に行う。

1. Git LFS の自動展開を止めた状態で `git clone` する
2. cloneしたリポジトリで `git lfs install --local` を実行し、Git LFS のフィルターをそのリポジトリだけで有効にする
3. `install` サブコマンドと同じ処理で、agentをcustom transfer agentとして登録する
4. そのリポジトリが指す論理プロファイルを、このPCのPC設定が持っているかを確かめる
5. `git lfs pull` で実体を取得する

利用者が知っておく必要があるのは、次の5点である。

**環境変数はagentが起動する `git clone` の子プロセスの環境へだけ渡る。** このコマンドは利用者のシェルの環境変数を書き換えないため、利用者が後から解除する必要はない。`GIT_CLONE_PROTECTION_ACTIVE=false` は安全の仕組みを切る指定であるため、agentは切ることとその理由を標準エラー出力へ書いてから渡す。

**利用者がディレクトリ名を省略すると、agentがURLの末尾から導いて表示する。** `https://github.com/owner/repo.git` からは、agentが `repo` を導く。`https://github.com/` のようにホストだけの綴りからは導かず、agentは第2引数での指定を促して失敗する。

**利用者が既に存在する空でないディレクトリを指定すると、`git` 自身がcloneを拒む。** agentはそのメッセージをそのまま利用者へ見せて失敗する。

```text
fatal: destination path 'origin' already exists and is not an empty directory.
git cloneに失敗しました: 終了コード128で終わりました
```

**途中で失敗しても、agentはcloneしたディレクトリを消さない。** 消す操作は破壊的であり、利用者が既に書き込んだものを巻き添えにするためである。`git clone` が成功して後段が失敗した場合、agentはどこへcloneしたかと、続きから再開する手順を標準エラー出力へ書く。

**このリポジトリが指す論理プロファイルをこのPCが持たない場合、agentは `git lfs pull` の前に止まる。** 他人のリポジトリを初めて取るときに必ず起きる詰まり方であり、そのまま `git lfs pull` を走らせるとGit LFS越しの分かりにくい失敗になるためである。出力は次の形になる。

```text
このリポジトリが指す論理プロファイルを解決できませんでした: 論理プロファイル'this-pc-does-not-have-it'がPC設定に定義されていません
PC設定の書き方は_doc/利用/PC初期設定.mdにあります。
複製した作業ツリーでdoctorを実行すると、不足の全体が分かります。
複製した作業ツリーは消さずに残しました: unknown-profile
原因を取り除いたあと、その作業ツリーで次を実行すれば続きから再開できます。
  git-lfs-rclone-storage doctor
  git lfs pull
```

**`clone` は `git clone` の他の引数を通さない。** `--branch` や `--depth` を渡すと、agentは未知の引数として失敗する。通す形にすると、agentが `git clone` の引数体系を実装することになるためである。それらが要る利用者は、次の節の4手順を使う。

### 従来の4手順

**このコマンドが使えない状況が3つあるため、本文書は従来の4手順も残す。**

- 利用者が `--branch` や `--depth` を指定したい場合。上のとおり `clone` はこれらを通さない
- そのPCへまだagentを配置していない場合。`clone` はagent自身が動くことを前提にする
- 利用者が既に `git clone` だけを済ませてしまった場合。この場合に必要なのは後半の3行だけである

手順は次の2つのブロックである。

```powershell
# 実行場所: cloneしたい親ディレクトリ
$env:GIT_CLONE_PROTECTION_ACTIVE = "false"
$env:GIT_LFS_SKIP_SMUDGE = "1"
git clone <リポジトリのURL>
Remove-Item Env:\GIT_CLONE_PROTECTION_ACTIVE, Env:\GIT_LFS_SKIP_SMUDGE
```

```powershell
# 実行場所: cloneされたリポジトリのルート
git lfs install --local
git-lfs-rclone-storage install
git lfs pull
```

`git lfs pull` が終わると、作業ツリーのpointerが実体に置き換わる。

### 2つの環境変数が必要な理由

`GIT_LFS_SKIP_SMUDGE=1` は、cloneの途中でGit LFSが実体を取りに行く動作を止める。この動作を止めないと、agentが未登録の状態で取得が試みられ、checkoutが失敗する。

`GIT_CLONE_PROTECTION_ACTIVE=false` は、Gitの「cloneの最中に出所不明なフックが有効化された」という保護を外す。Git LFS が登録するフックは正規のものであり危険ではないが、Gitはclone時にそれを区別できない。この保護に引っかかると、cloneは次のメッセージで止まる。

```text
fatal: active `post-checkout` hook found during `git clone`:
For security reasons, this is disallowed by default.
If this is intentional and the hook should actually be run, please
run the command again with `GIT_CLONE_PROTECTION_ACTIVE=false`
```

なお、この保護に引っかかるのは、そのPCでGit LFSのフックが全リポジトリ向けに登録されている場合である。引っかからない環境でも、この環境変数を付けて困ることはない。

### 環境変数を付けずにcloneしてしまった場合

cloneをやり直す必要はない。次のエラーが出た状態からでも、上記の後半3行を実行すれば同じ状態に到達する。

```text
Downloading payload.bin (300 KB)
Error downloading object: payload.bin (3cdc92c): Smudge error: Error downloading payload.bin (3cdc92c...):
  error transferring "3cdc92c...": [0] remote missing object 3cdc92c...
error: external filter 'git-lfs filter-process' failed
fatal: payload.bin: smudge filter lfs failed
warning: Clone succeeded, but checkout failed.
You can inspect what was checked out with 'git status'
and retry with 'git restore --source=HEAD :/'
```

**`warning: Clone succeeded, but checkout failed.` を見ても故障だと判断してはならない。** cloneそのものは成功しており、実体の取得だけが未了である。ここに出ている `[0] remote missing object` は Git LFS 自身が出すメッセージであり、本基盤のエラーコード表の0番ではない。

### 導入は「PCとリポジトリの組ごと」である

2回目以降のcloneにも同じ手順が要る。同じPCで同じリポジトリを2箇所へcloneした場合、利用者はそれぞれで `git-lfs-rclone-storage clone` を使うか、`git lfs install --local` と `git-lfs-rclone-storage install` を実行する。Git設定はリポジトリごとに持たれるためである。
