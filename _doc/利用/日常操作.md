# 日常操作

この文書は、導入が終わった後に日常的に行う操作を説明する。ここに書く内容は、`git clone` / `git checkout` / `git lfs pull` / `git push` のときに何が起きるかと、複数のPCで使うときに何を知っておけばよいかである。

導入そのものは [PC初期設定.md](PC初期設定.md) と [プロジェクト導入.md](プロジェクト導入.md) が扱う。失敗したときの調べ方は [トラブルシューティング.md](トラブルシューティング.md) が扱う。

## 実体が置かれる3箇所

大容量資産の実体は、次の3箇所に置かれる。この3箇所の役割を区別することが、日常操作を理解する出発点である。

| 場所 | 中身 | どのドライブか |
|---|---|---|
| 作業ツリーのファイル | 実体そのもの | ローカルディスク |
| `.git/lfs/objects/` | Git LFS のローカルキャッシュ | ローカルディスク |
| `<base_path>/lfs/objects/` | 保管先のオブジェクト | マウント先（例: `G:`） |

**マウントしたドライブは push 先でしかない。** 作業ツリーの資産はローカルディスク上の実ファイルであり、日常のビルドや読み込みはマウント先に一切触れない。マウント先へ触れるのは、`git push` で書くときと、ローカルキャッシュに無いオブジェクトを取得するときの2つだけである。

保管先でのオブジェクトのパスは、ファイルの内容から決まる。oidとは、Git LFS がファイルの内容から計算する64文字の識別子（SHA-256）のことである。

```text
<base_path>/lfs/objects/sha256/<先頭2文字>/<次の2文字>/<64文字のoid>
```

このパスは、元のファイル名・拡張子・プロジェクト名・PC名を含まない。したがって、同じ内容のファイルは複数のプロジェクトで同じパスを共有する。agentはオブジェクトを変更しないものとして扱い、内容の更新を新しいoidのオブジェクトの追加として表す。古いオブジェクトは変化しない。

## 各操作で何が起きるか

### `git clone`

**初回のcloneは特別な手順が要る。** 手順の全量は [プロジェクト導入.md](プロジェクト導入.md) の「初回clone」にある。通常の `git clone` だけでは、agentが未登録のため実体を取得できない。

### `git checkout`

ブランチを切り替えると、Git LFS はそのコミットが参照するoidの実体を作業ツリーへ展開する。実体をどこから持ってくるかは、次の順で決まる。

1. `.git/lfs/objects/` にそのoidがあれば、そこからコピーする。ネットワークも保管先も使わない。
2. 無ければ、agentを起動して保管先から取得する。

一度取得したオブジェクトはローカルキャッシュに残るため、同じブランチを行き来してもマウント先への読み取りは1回で済む。

### `git lfs pull`

作業ツリーに残っているpointer（実体の代わりにGitへ記録される参照情報）を実体へ置き換える。既に実体になっているファイルは何もしない。次の2つの場面で使う。

- 初回cloneの最後の手順として使う。
- 保管先の障害で取得に失敗した後、原因を直してから再取得するために使う。

### `git push`

Gitのオブジェクト（コミット・ツリー・pointer）をリモートへ送る前に、Git LFS がpointerの指す実体をagentへ渡す。agentは保管先に同じoidが既にあるかを確かめ、無ければ書き込む。**同じoidを再びpushしても、保管先のオブジェクトは増えない。**

ローカルディレクトリ方式では、`git push` の成功はマウント先への書き込みが完了したことを意味する。クラウドへの実際の送信は Google Drive for Desktop が後で行う。この点は [PC初期設定.md](PC初期設定.md) の「2つの方式の違い」で説明している。

pushの途中でLFSの転送だけが失敗した場合、Gitのrefの更新も失敗する。原因を直した後、`git lfs push --all origin` で実体だけを送り直せる。

## ローカルディスクの消費

**資産容量のおよそ2倍をローカルディスクが消費する。** 作業ツリーの実ファイルと `.git/lfs/objects/` のキャッシュの2つが、同じ内容を別々に持つためである。これはGit LFS の仕組みによるものであり、この基盤に固有の性質ではない。

キャッシュのうち、どのブランチからも参照されなくなった古いオブジェクトは、次のコマンドで消せる。

```powershell
# 実行場所: 対象のGitリポジトリのルート
git lfs prune
```

`git lfs prune` はローカルキャッシュだけを消す。**保管先のオブジェクトは消さない。** 消したオブジェクトが後で必要になれば、保管先から取り直せる。

Git LFS には、作業ツリーとキャッシュで同じ実体を共有してディスク消費を半分にする `git lfs dedup` というコマンドもあるが、**このコマンドはコピーオンライト（書き込みが起きたときだけ実体を複製するファイルシステムの機能）に対応したファイルシステムを必要とする。** WindowsのNTFSは対応していないため、実行すると次のように断られる。

```text
This system does not support de-duplication.
```

したがって、利用者はWindows上では2倍の消費を前提に空き容量を見積もる。

## 2台以上のPCで使う

### 揃えるもの

| 揃えるもの | どこにあるか |
|---|---|
| 論理プロファイル名 | PC設定の `[profiles.<名前>]` と、プロジェクトの `.large-assets.toml` の `profile` |
| Git LFS の対象パターン | リポジトリの `.gitattributes`（コミットされているため自動的に揃う） |
| 保管先の中身 | 同じGoogleアカウントの同じフォルダを両方のPCから見る |

### 揃えなくてよいもの

| 揃えなくてよいもの | 理由 |
|---|---|
| 保管先の絶対パス（`base_path`） | PCごとにドライブ文字が違ってよい |
| rcloneのリモート名（`rclone_remote`） | PCごとのrclone設定に存在する名前でよい |
| 保管方式（`storage`） | 片方がマウント方式、もう片方がrclone方式でもよい |
| agentの実行ファイルの置き場所 | `install` が各PCで絶対パスを登録する |

**論理プロファイル名だけを揃えれば足りる**という点が、この基盤の設計の核心である。プロジェクトは保管先の実体を知らないため、PCごとの事情はPC設定の中に閉じる。

### 2台目のPCで行うこと

1. [PC初期設定.md](PC初期設定.md) の手順1から手順5までを行う。
2. [プロジェクト導入.md](プロジェクト導入.md) の「初回clone」の手順でリポジトリを取得する。
3. `git-lfs-rclone-storage doctor` で11項目すべてが `[OK]` になることを確かめる。

`.gitattributes` と `.large-assets.toml` は既にコミットされているため、2台目で作り直す必要はない。

## 保管先へ到達できないとき

ここでいう offline とは、保管先へ到達できない状態のことである。回線が切れている状態と、保管先のドライブがマウントされていない状態の両方を指す。この状態で利用者ができることとできないことを、次に分けて示す。

### できること

- ローカルキャッシュにあるオブジェクトを使う `git checkout`。作業ツリーのファイルを読む操作すべて。
- `git add` と `git commit`。コミットに入るのはpointerだけであり、実体の転送はpushまで起きない。
- `git log` / `git diff` / `git branch` などの履歴操作。

### できないこと

- `git push`。実体の書き込みに失敗し、Gitのrefの更新も失敗する。
- ローカルキャッシュに無いオブジェクトを必要とする `git checkout` と `git lfs pull`。

マウント方式では、利用者は2つの状態を区別する必要がある。第1の状態は、Google Drive for Desktop の同期が止まっている状態である。この状態では書き込みは成功し、クラウドへの送信だけが遅れる。他のPCがこの間にpullすると、そのPCはコード11で失敗する。復旧の手順は [トラブルシューティング.md](トラブルシューティング.md) の「クラウドへの同期の遅れ」にある。第2の状態は、ドライブそのものがマウントされていない状態である。この状態では `doctor` の「保管先ルートディレクトリの存在確認」が失敗する。

到達できない状態での作業が終わったら、利用者は接続を回復してから `git push` をやり直す。コミットは既にできているため、作業をやり直す必要はない。
