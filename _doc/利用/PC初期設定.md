# PC初期設定

この文書は、1台のPCでこの基盤を使えるようにするまでの手順を説明する。ここに書く作業は**PCごとに1回**行えばよく、対象のGitリポジトリが増えても繰り返す必要はない。リポジトリごとの作業は [プロジェクト導入.md](プロジェクト導入.md) が扱う。

## 最初に: Google Cloud Console を開く必要はない

既定の保管方式は、Google Drive for Desktop がマウントしたドライブへ直接書き込む方式である。この方式では rclone も OAuth 認証（Googleアカウントの利用許可をアプリへ与える手続き）も不要であり、**Google Cloud Console を一度も開かない**。

この文書がこの注意を先に置く理由は2つある。第1に、rclone を使う方式では `rclone config` の画面が「自分のアプリ識別子を作ることを強く推奨する」と案内するため、利用者が案内に従うと Google Cloud Console での長い回り道に入る。第2に、その回り道の終点へ個人のGoogleアカウントでは到達できないことが実地で判明している。この2つの事情の詳細を、本文書は末尾の「rclone を使う場合」に置く。

利用者は、マウントできない保管先（S3、Backblaze B2、SFTPなど）を使う場合に限り、末尾の節を読めばよい。

## 全体の順序

```text
Google Drive for Desktop を導入する
  → Googleアカウントでサインインする
  → マウント先に保管フォルダを作る
  → PC設定 config.toml を作る
  → agentの実行ファイルを配置する
```

この5段階が終われば、そのPCでの準備は完了である。設定が揃ったかどうかの判定は `doctor` が行うが、`doctor` はGitリポジトリの設定も同時に見るため、全項目が合格するのは [プロジェクト導入.md](プロジェクト導入.md) の手順まで終えた後になる。

## 手順1: Google Drive for Desktop を導入する

```powershell
# 実行場所: どのフォルダでもよい
winget install Google.GoogleDrive
```

導入後は**新しいPowerShellを開く**。wingetはPATH（実行ファイルを探すディレクトリの一覧）を書き換えるが、起動済みのシェルは古いPATHを引き継いでいるため、同じシェルでは新しいコマンドが見つからない。

## 手順2: Googleアカウントでサインインする

Google Drive for Desktop を起動し、資産を置きたいGoogleアカウントでサインインする。サインインが完了すると、Windowsのエクスプローラーにドライブ文字（`G:` など）が割り当てられる。割り当てられた文字は環境によって違うため、エクスプローラーで実際の文字を確認する。

## 手順3: マウント先に保管フォルダを作る

割り当てられたドライブの下に、この基盤専用のフォルダを1つ作る。

```powershell
# 実行場所: どのフォルダでもよい
New-Item -ItemType Directory "G:\マイドライブ\git-lfs-rclone-storage"
```

このフォルダの下に `lfs\objects\sha256\...` という構造ができる。フォルダの中身を手で編集してはならない。

## 手順4: PC設定を作る

PC設定とは、論理プロファイル名と、そのPCでの実際の保管先との対応を書くファイルのことである。置き場所は次のパスに固定されている。

```text
C:\Users\<ユーザー名>\AppData\Roaming\git-lfs-rclone-storage\config\config.toml
```

内容の全量は次の4行である。

```toml
schema_version = 1

[profiles.personal-large-assets]
storage = "local"
base_path = "G:/マイドライブ/git-lfs-rclone-storage"
```

- `profiles.` に続く `personal-large-assets` が論理プロファイル名である。この名前を、各Gitリポジトリの `.large-assets.toml` の `profile` と一致させる。
- `storage = "local"` は、マウント済みのパスへ直接読み書きする方式を選ぶ指定である。
- `base_path` には手順3で作ったフォルダの絶対パスを書く。区切りは `/` でも `\` でもよい。

**このファイルへ認証トークンやパスワードを書かない。** ローカルディレクトリ方式では、そもそも認証情報をこのツールが持たない。Googleアカウントの認証は Google Drive for Desktop が持つ。

**`temp_directory` は廃止した。** 古い手順に従って書いてしまっても動作は壊れないが、`doctor` が「読まれていないので削除してよい」と注記する。

## 手順5: agentの実行ファイルを配置する

本リポジトリのソースからビルドし、`cargo clean` で消えない場所へ実行ファイルを置く。

```powershell
# 実行場所: このリポジトリ（git-lfs-rclone-storage）のルート
cargo xtask install-binary
```

このコマンドはreleaseプロファイルでビルドし、Cargoの `bin` ディレクトリへ実行ファイルを置き、配置先の絶対パスを表示する。rustup で Rust を導入していれば、このディレクトリはPATHに通っている。通っていない場合は、そのことと対処をコマンドが案内する。**このコマンドはPATHを書き換えない。** 環境変数の変更は他のソフトへ影響し、元へ戻す手段を利用者が持たないためである。

配置できたかどうかは、新しいPowerShellで次を実行して確かめる。

```powershell
# 実行場所: どのフォルダでもよい
git-lfs-rclone-storage help
```

使い方の一覧が表示されれば配置は完了である。

## このファイルはコミットする / しない

PC初期設定で作るファイルは、いずれもGitの管理対象にしない。

| ファイル | 置き場所 | コミットするか | 理由 |
|---|---|---|---|
| PC設定 `config.toml` | `C:\Users\<ユーザー名>\AppData\Roaming\git-lfs-rclone-storage\config\config.toml` | しない | PCごとに違う保管先の絶対パスを持つ |
| rclone設定 `rclone.conf` | `C:\Users\<ユーザー名>\AppData\Roaming\rclone\rclone.conf` | しない | リモート定義とOAuthトークンを持つ |
| agentの実行ファイル | Cargoの `bin` ディレクトリ | しない | ビルド生成物である |
| 保管先のオブジェクト | `<base_path>\lfs\objects\...` | しない | Git LFS が管理する実体であり、Gitのツリーには入らない |

これらのファイルはどれも、そもそもGitリポジトリの中に置かれない。Gitへコミットするファイルは [プロジェクト導入.md](プロジェクト導入.md) の表が扱う。

## 保管先を変える

保管先を別の場所（別のクラウド、別のドライブ、rclone対応の外部保管先）へ移すとき、**変更するのはPC設定だけである。** Gitリポジトリ側の `.gitattributes` と `.large-assets.toml` は変更しない。コミット履歴も変わらない。

手順は次の3段階である。

1. 現在の `base_path` の下の `lfs` ディレクトリを、新しい保管先へそのまま複製する。ディレクトリ構成を変えてはならない。オブジェクトのパスは内容から決まるため、複製先でも同じパスでなければならない。
2. PC設定の `base_path`（rclone方式なら `rclone_remote` も）を新しい保管先へ書き換える。
3. 対象のGitリポジトリで `git-lfs-rclone-storage doctor` を実行し、全項目が合格することを確かめる。

複製先の保管先からGit側を一切変更せずに同じコミットを復元できることは、受入条件の実証で確認済みである（[_doc/開発スレッド/2026-08-27_v1受入条件1-9番実証.md](../開発スレッド/2026-08-27_v1受入条件1-9番実証.md)）。

複数のPCで使っている場合は、PCごとにPC設定を書き換える。論理プロファイル名を変えなければ、Gitリポジトリ側は移行を知る必要がない。

## rclone を使う場合

保管先がドライブとしてマウントできない場合（S3、Backblaze B2、SFTPなど）は、rclone を子プロセスとして起動する方式を選ぶ。ここから先は**既定の手順ではない。** マウント方式で足りるなら読む必要はない。

### 2つの方式の違い

| 比べる点 | ローカルディレクトリ方式（既定） | rclone方式 |
|---|---|---|
| PC設定 | `storage = "local"` と `base_path` の2行 | `rclone_remote`・`base_path` ほか |
| 必要な導入物 | Google Drive for Desktop | rclone |
| 認証 | Googleアカウントでサインインするだけ | `rclone config` での対話 |
| 使える保管先 | ドライブとしてマウントできるもの | rcloneが対応するすべて |
| `git push` の成功が意味すること | ローカルへの書き込みが完了したこと。クラウドへの送信は同期クライアントが後で行う | 転送が完了したこと |

最後の行が示す違いは正直に受け止める必要がある。マウント方式では、`git push` の直後に電源が落ちたり回線が切れたりすると、pointer（実体の代わりにGitへ記録される参照情報）だけが先に共有される可能性がある。ただし壊れ方は安全であり、取得側は「オブジェクトが存在しません（コード11）」と明示的に失敗する。復旧は `git lfs push --all origin` で送り直すだけである。

### rclone の導入と設定

```powershell
# 実行場所: どのフォルダでもよい
winget install Rclone.Rclone
```

導入後は**新しいPowerShellを開く**。手順1と同じ理由である。

```powershell
# 実行場所: どのフォルダでもよい
rclone config
```

`rclone config` はカレントディレクトリを見ない。設定の書き込み先は `C:\Users\<ユーザー名>\AppData\Roaming\rclone\rclone.conf` に固定されている。何も設定していない状態で `No remotes found, make a new one?` と表示されるのは正常である。

### client_id と client_secret は空のまま Enter する

Google Drive を選ぶと `client_id>` の入力を求められ、「rclone共用の識別子は2026年中に停止するため、自分の識別子を作ることを強く推奨する」という案内が表示される。**この案内に従わず、`client_id>` と `client_secret>` の両方を空のまま Enter を押す。**

空でよい理由は次の2つである。第1に、rclone が用意するOAuthクライアントはrclone側でGoogleの審査を通しているため、警告画面が出ずに認証が通る。第2に、自分の識別子を作る道は、後述のとおり個人のGoogleアカウントでは最後まで進めない。

### 案内に従って Google Cloud Console を開いてしまった場合

既に開いてしまった利用者が戻れるように、途中で止まる順路を記録する。作ったプロジェクトは放置してよく、費用は発生しない。

1. `rclone config` の案内に従い、Google Cloud Console でプロジェクトとOAuthクライアントを作る。
2. ブラウザ認証で「アクセスをブロック: (アプリ名) は組織内でのみ利用可能です」と表示される。同意画面のユーザーの種類が「内部」になっているためである。
3. ユーザーの種類を「外部」へ変更する。すると公開ステータスが「テスト中」になる。
4. 「アプリを公開」を押そうとすると、アプリのドメイン・プライバシーポリシー・利用規約の入力を求められて進めない。
5. ここで止まる。

止まる理由は、`https://www.googleapis.com/auth/drive`（Driveへのフルアクセス）を Google が制限付きスコープに分類しているためである。制限付きスコープを使うアプリを本番環境へ公開するには、自分が所有しSearch Consoleで所有権を確認したドメインと、その上に置いたホームページ・プライバシーポリシー・利用規約が要る。ドメインを持っていない利用者は越えられない。

「テスト中のまま使う」という選択も採れない。Googleの公式文書は、公開ステータスが「テスト中」の外部アプリには**7日で失効するリフレッシュトークンが発行される**と記している。使用の有無を条件にしていないため、発行から7日という絶対の期限である。これに賭けると、導入の1週間後に `git push` や `git lfs pull` が突然失敗する。

7日の期限を避ける代替としてサービスアカウントが挙がることがあるが、**現時点では推奨しない。** rclone の公式文書には、サービスアカウントを個人のGoogle Driveで使ったときの保存容量の扱いに関する記述が無い。サービスアカウント自身が保存容量を持たないという既知の問題があり、個人アカウントのDriveへ書き込めない可能性がある。検証していないため、手順として書かない。

### 共用の識別子が停止したときの移行先

rclone公式は共用の識別子を2026年中に停止すると告知している。停止したときの移行先は `drive.file` スコープである。`drive.file` は制限付きスコープではないため、審査もドメインもプライバシーポリシーも不要で自分の識別子を公開できる。この基盤はオブジェクトを全部自分で作るため、自分が作ったファイルだけ見えれば足りる。

移行そのものは `rclone config` で該当リモートを編集して識別子と秘密鍵を入れ直すだけであり、保管済みのオブジェクトもGit側の設定もやり直しにならない。

未検証の点が1つある。`drive.file` は「アプリが作ったファイル」への権限であるため、2台のPCが同じ識別子を使ったときに、片方が作ったオブジェクトをもう片方から見えるかを確かめる必要がある。停止が近づいた時点で検証する。

### rclone方式のPC設定

```toml
schema_version = 1

[profiles.personal-large-assets]
rclone_remote = "mega-assets"
base_path = "git-lfs-rclone-storage"
transfer_timeout_seconds = 3600
```

- `rclone_remote` には、そのPCの `rclone config` で作ったリモート名を書く。**この名前は2台のPCで違っていてよい。** 揃えるのは論理プロファイル名だけである。
- `rclone_executable` を書けばrcloneの実行ファイルのパスを明示でき、省略するとPATHから `rclone` を探す。
- `storage` キーを省略した場合、rclone方式として扱われる。

**client_id と client_secret は秘密情報である。** これらの値はrcloneの設定ファイルだけが持ち、本リポジトリにも対象プロジェクトにもコミットしない。
